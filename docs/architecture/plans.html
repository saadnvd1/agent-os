Plans, pieces and stacks

A plan is written and approved before code. A big plan splits into several pull requests only for a reason the code can check.

A task that plans first

Pieces: one PR by default

Stacks: a board's cards as stacked PRs

Key states

planning
The agent is writing the plan.
awaiting
Plan written, waiting for approval. No agent runs.
implementing
Approved; the task builds.
waiting piece
A registered piece whose dependency hasn't merged or deployed.
folded
A piece with no standing reason, built inside the one before it.

In plain words

The planning step and its approval are what the review later judges the PR against: every approval is written into the task's brief.

Nothing about pieces is silent. A Pieces block that can't be read, a count that doesn't match its items, or a repo that isn't a project of the workspace holds the task for approval and tells the orchestrator.

Signing off a stacked card whose parent hasn't merged is refused: the stack gate. Land is the way to merge a stack in order.

Key files
